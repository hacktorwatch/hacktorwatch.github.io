01 / GET TO KNOW THE DEVICE

Start with the design.

The watch combines an ESP32-S3, external memory, motion sensing, a round touch display, audio and haptics. Open the schematic and the mechanical files to understand how those pieces fit together.

Schematics and PCB design →Mechanical design files →Original hardware block diagram →

Use the schematic for your board revision and the overlay or pin configuration for your selected firmware. The project’s block diagram and individual firmware examples can use different bus labels.

02 / PICK YOUR TOOLS

Choose a firmware path.

These are separate implementations. Choose the environment that matches your experiment, then read its setup instructions and current feature support.

ArduinoPlatformIO example, watchface, steps, wrist wake and BLE time sync.NuttXPOSIX-oriented development, shell and board-port infrastructure.ZephyrDevicetree, Kconfig, LVGL and an RTOS application structure.

The NuttX port lives in a separate repository with submodules. Follow that port’s README when cloning and building it.

03 / MAKE SOMETHING SMALL WORK

Give your first app one job.

Begin with the existing display example and get a visible result. Then add one input or behaviour at a time.

  1. Say hello. Build the selected firmware and confirm that the display and input paths work.
  2. Show a value. Read the IMU counter or battery gauge, then update a label.
  3. Make it interactive. Add touch behaviour, a watchface complication or an application state.
  4. Connect it. Explore the Arduino BLE time-sync example, or design a GATT interface for your own application.
The current Zephyr application reads the IMU’s raw step counter while the display is active and refreshes it on wake. Treat that as a counter since sensor reset, rather than a persisted daily total. The existing Arduino example has its own counter and persistence implementation.

For local machine learning, a small TensorFlow Lite Micro wake-word detector has already run on Hacktor Watch. Use that as a starting point for thinking about audio buffers, model working memory and listening time.

04 / LEARN FROM THE ACTUAL DEVICE

Build. Observe. Adjust.

Follow your stack’s build and flash instructions for the actual board. Once the application runs, check the whole experience: sensor updates, display work, wireless behaviour and power use.

Keep notes about your hardware revision, firmware version and workload. A configured timer interval is a software choice; measured response time and energy use come from testing the device.

05 / BUILD IN THE OPEN

Share what you learn.

Found an issue, improved a driver or made an interesting application? Share the relevant details with the project so another developer can reproduce the result.
